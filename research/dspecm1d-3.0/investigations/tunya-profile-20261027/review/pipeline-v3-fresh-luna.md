# Fresh Luna review: baseline adapter, supervisor v3, and configs v5

**Verdict: PASS for the reviewed data adapter, supervisor delta, and configs-v5 wiring.** This was a read-only static review. I did not build or run a solver, run the campaign, or use SSH. Reported synthetic tests and profile-02 solver results were not independently repeated here.

The adapter’s units and data contract match the frozen DSpec trace writer and YSpec reader. It requires the exact trace header, 1024 numeric rows on the 0–5115 s grid at 5 s spacing, finite time/displacement/window values, and Hann weights matching the 1000–1200 s window. It separately requires removed rows 721–1023 to have exact zero weights. Energy is computed as `0.5 * 5 s * window_weight * vertical_m^2`, so its units are m²·s; `math.fsum` must give exactly equal positive full and prefix totals. The output is the original header and first 721 data rows copied byte-for-byte. Input/output hashes, counts, grid/window metadata, and energy are recorded in a fresh receipt; existing outputs and input/output path collisions are refused. This matches YSpec’s parser, which requires 721 samples on the same 5 s grid through 3600 s and recomputes the same Hann window. It changes the input file length for the parser while preserving all windowed samples and their byte representation.

The supervisor-v3 diff is limited to distinguishing nonblocking `EAGAIN` from true pipe EOF and adding post-cleanup output draining. The drain now checks its deadline on every pass, including while data remains continuously readable, and records an incomplete-drain detail if EOF is not observed within the bounded interval. This closes the continuous-writer hang found in the initial review. The existing thread/RSS/timeout sampling, `(PID,start-time)` identity tracking, TERM/KILL cleanup, reaping, cleanup verification, input/output hashes, and failed/unclean status handling remain in place. The established limitation remains: userspace `/proc` polling is not kernel aggregate resource enforcement and may miss processes shorter than a poll.

The v5 plan adds four sequential prefix jobs, each after its matching DSpec trace exists and before the corresponding YSpec jobs. YSpec kernel commands and hashed inputs point to the generated prefix; their DSpec radial-node inputs remain the matching run’s output. The plan still has a 50-thread ceiling. The receiver and all six L=3 solver executable paths remain the reviewed v4 paths; the DSpec jobs are unchanged, and the strict qualification checker command and physical parity gates remain unchanged. The added explanatory note records the parser correction and preserved profile-02 failure.

This PASS covers static data-path and plan consistency. It does not independently validate the reported profile-02 outputs or establish scientific accuracy.

## Final preservation-only delta

A follow-up diff review found only one change in the active `prefix_trace.py`: it no longer removes a newly written prefix CSV or receipt if a later step fails. The prefix and receipt still use exclusive creation, and the input-change check still occurs after the prefix is flushed. Thus a detected input mutation or receipt-write failure leaves the already-created evidence in place for audit; the failed job must be preserved and any retry use a fresh task directory. The previous implementation remains preserved as `prefix_trace-pre-preservation.py`. The implementation owner reports that an input-change-after-write synthetic case confirmed retention of the prefix without a receipt; I did not rerun that test. This preservation change does not alter the validated CSV bytes, row/window checks, energy calculation, supervisor, or configs-v5 plan. **The PASS above remains unchanged.**
