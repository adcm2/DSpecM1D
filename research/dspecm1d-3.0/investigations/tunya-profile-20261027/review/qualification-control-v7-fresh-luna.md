# Fresh Luna review: control qualification checker and profile plan v7

**Verdict: HOLD on assessment provenance; other reviewed gate and dispatch contracts are consistent.** This was a read-only static review. No source was edited, and I did not build, run scientific jobs, or use SSH.

## Qualification checker

`tools-v4/qualification_checks_control.py` imports the frozen `tools/qualification_checks.py` through a path relative to its own location. The v7 job declares both files as inputs, matching that import. The frozen checker remains responsible for the six original L3 jobs, including exact native/profile outputs, complete grids and 179 radial nodes, finite values, DSpec q-dot-P/(2E) at `1e-10`, metadata and CSV contracts, and the existing descriptive cross-code checks.

The adapter retains original v4/v6 per-channel/per-column error metrics and locations as historical results. It does not turn the original mismatch into a pass. It separately compares the analytic control against both v6 variants at the unchanged `2e-13` threshold for all six kernel channels and each trace/spectrum column, checks matching physical options and domain fields, checks energy fields, and compares all radial nodes. `PASS_WITH_ANALYTIC_REFERENCE_CONTROL` is selected only when the separate control comparison passes and original v4/v6 parity fails; a control failure sets overall `FAIL`. The old-v4/control comparison is diagnostic only. The additional control is also read through the frozen DSpec loader, which applies the complete L3, finiteness, radial-count and q-dot-P gates. Both receiver-gate predecessors must precede the control job in state, have completed with return code zero and unchanged inputs, and have log SHA-256 values matching the saved logs.

## Provenance blocker

The first `qualification-checks` job assesses the saved `continuation/profile-04` task, but its declared supervisor inputs contain only the adapter, frozen checker, and `profile-04/state.json`. The checker reads the six L3 jobs’ result JSON, CSVs, kernel binaries, radial-node data, and job logs without verifying those jobs’ state status or their `outputs_sha256`/`log_sha256` entries. Only the two receiver-gate predecessor logs receive explicit state-hash verification. The supervisor hashes declared inputs and file-valued command arguments; the profile-04 directory command argument is not a file, so the six L3 artifacts are not protected by the assessment job’s before/after input manifest. A changed or partial artifact set could therefore be assessed without a mismatch against the recorded completed-job hashes. Bind the full assessment read set or verify every profile-04 job’s state, completion, and saved output/log hashes before treating the assessment as provenance-closed.

## High-degree plan

The v7 plan has 26 serial jobs with a maximum configured thread cap of 50; numerical jobs are pinned to CPU 0, and the reviewed supervisor forces numerical-thread environment variables to one. It starts with the data-only profile-04 assessment, then writes new profile-05 results using the existing build-03 executables. The physical probes cover degrees 128 and 384 for DSpec v4/v6 native/profiled and YSpec native/profiled; degree 1536 uses DSpec v6 and YSpec native/profiled. Probe commands use 64 angles and the `kernel-probe` mode, so they are diagnostics and do not claim full global high-degree kernels. YSpec waveform jobs are distinct from its kernel-probe jobs. The plan includes trace-prefix adapters before the YSpec runs that consume those prefixes. No solver, threshold, binary, or build is changed by this plan.

The job order, explicit paths, degree settings, per-job time/memory limits, and 50-thread ceiling are statically consistent with the described bounded campaign. This HOLD concerns the read-only profile-04 assessment’s incomplete input-hash binding, not the high-degree plan’s job sequence. No remote filesystem state or scientific result was verified.
