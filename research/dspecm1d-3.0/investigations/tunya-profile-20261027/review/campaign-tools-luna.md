# Independent Luna review: campaign build and supervision tools

**Scope:** read-only review of `tools/build_campaign.py`, `tools/supervise_campaign.py`, and `tools/README.md` for safe detached Tunya execution, resource tracking, evidence preservation, fail-closed resume, and build consistency. No remote command or scientific run was launched. One small synthetic resume probe used a disposable directory under `/tmp`.

## Decision

**Do not use these tools for a remote science campaign yet.** The design has useful safeguards (fresh roots, sequential job execution, exact command records, SHA-256 evidence, PID/start-time identities, thread polling, optional RSS/timeout stops, and failed-output retention), but I found concrete fail-closed and cleanup gaps. The defects below need correction and independent review before launch. The YSpec compile manifest and Tunya host's SSH/session policy also remain unverified deployment gates.

## Blocking findings

1. **Resume can silently start a new run when task state is missing.** In `supervise_campaign.py:139-145`, `--resume` loads prior state only if `state.json` exists; otherwise it creates a fresh running state and executes the plan. A synthetic probe created an existing empty task directory with no state, then invoked `--resume`; the supervisor returned success, ran the job, and marked it completed. Fail closed by requiring an existing, valid state file for every resume, verifying its task ID and schema, and refusing missing/malformed state. See `:134-145`.

2. **Timeout cleanup can be reported without proving descendants exited.** `signal_owned` suppresses identity-read and `os.kill` errors (`:77-85`). On a limit breach, the loop sends TERM, sleeps 0.5 s, takes one new snapshot, sends KILL, then exits the monitor (`:237-242`). It waits only for the leader and records failure without verifying every tracked `(PID,starttime)` is gone (`:261-280`). Make signaling errors visible; after escalation keep polling identity-checked owned processes until none remain or a bounded cleanup deadline expires, and record cleanup failure as an unclean terminal state. Do not claim cleanup succeeded when a worker remains.

3. **Periodic ancestry snapshots can lose detached/reparented descendants.** `proc_table()` silently drops unreadable or transient `/proc` entries (`:36-51`), and ownership is extended only by current PPID ancestry (`:54-64,215-216`). A child that forks, calls `setsid()`, and is reparented between 100 ms polls can disappear from the owned set; later identity cleanup will not find it. The README's userspace/polling caveat is accurate, but this is not complete descendant containment. For a hard stop guarantee, use a cgroup or subreaper-based owner; at minimum make `/proc` inspection failures visible, explicitly disallow daemonization/double-forking in the plan contract, and test a synthetic `setsid()` escape and cleanup case.

4. **The documented detached log command can overwrite prior evidence.** README `:82-85` uses `> supervisor.log`, which truncates an existing file. Require a fresh unique attempt-specific log path and an exclusive-create/no-clobber check before starting. The campaign tree's task ID is unique by default, but the log sits outside that task folder and is not protected by the supervisor's lock.

5. **`compiler_jobs <= 2` is validated as a number but not enforced on the command.** `build_campaign.py:69-72` bounds the setting, while `:47-55,102-118` permits arbitrary argv and substitutes `{JOBS}` only if the config includes it. A command can omit the token or request `-j 8`/`--parallel 8`; in that case the validated setting has no effect. The README says to add exact commands but offers no cap check. Require the command to consume the validated job limit through a constrained build wrapper or validate supported build-system parallel flags and reject contradictory/unbounded commands.

## Required pre-launch evidence / additional checks

- The builder does not compare paired native/profile command flags or establish that all 14 YSpec translation units use the same reviewed compiler definitions and optimization flags. The README deliberately delegates exact commands and file lists to the campaign owner (`:34-45`). Before launch, review the actual Tunya manifest: list every YSpec source/TU and dependency, show a common flag set with only intentional instrumentation differences, and verify complete source/dependency fingerprints. This is a configuration gate, not evidence supplied by the current tools.
- The README `nohup` invocation redirects stdin/stdout/stderr and should ignore ordinary SIGHUP on a conventional host. It does not establish survival under Tunya's SSH/session manager or systemd `KillUserProcesses` policy. Validate that policy with a harmless detached heartbeat on Tunya before a science campaign; do not treat a local synthetic test as proof of remote persistence.
- Thread accounting is a periodic userspace snapshot, not an instantaneous hard 50-thread ceiling. It counts the supervisor plus observed owned process threads (`:215-217,229-233`) and forces common OpenMP/BLAS variables to one (`:23-25,147-150`). The README discloses polling limits and shared-RSS double counting (`:94-100`). Preserve that wording in campaign records and use kernel/cgroup limits if a hard aggregate ceiling is required.
- `memory_gib` is optional, as requested (`:229-233`, README `:71-79`); when configured it compares observed descendant RSS to the limit. Record the chosen threshold and watchdog caveats in each plan/result.

## Positive controls observed

The supervisor executes jobs sequentially, caps configured thread limits at 50, records command hashes, checks the unchanged plan hash on resume, verifies completed-job log and declared-output hashes, refuses an existing task without `--resume`, refuses incomplete prior job directories, and keeps failed partial outputs in place (`supervise_campaign.py:120-145,152-188,261-280`; README `:49-80,89-100`). The builder refuses a nonempty build root, caps the configured job field at two, makes variant directories, fingerprints declared inputs before and after each build, records command/log/binary hashes, and stops on the first failed or input-mutating build (`build_campaign.py:63-71,87-144`). These are useful controls, but they do not resolve the blockers above.

**Disposition:** no remote launch or science run until findings 1–5 are fixed or explicitly covered by an independently reviewed enforcement wrapper, and the actual Tunya build/run manifests and detached-session behavior have been reviewed. Keep the disposable synthetic probe result separate from campaign evidence.
