# Fresh Luna review: qualification checker v2

**Verdict: PASS for the qualification checker’s static contract and source-schema alignment.** This is a read-only review of `tools/qualification_checks.py`, its README/status notes, and the actual frozen DSpec v4/v6 and YSpec v6 drivers. I did not run the checker, a build, a scientific calculation, or SSH/remote work; the synthetic tests mentioned in the status notes are implementation evidence, not tests independently repeated here.

- The actual DSpec drivers write the fields checked by the gate: physical options including `qex`, source/receiver and element flags, result energy values, and the domain’s complete-grid, radial-count, binary-size, layout and q-dot-P metadata. The new metadata checks compare stable native/profile result and domain records while excluding elapsed time, path-bearing fields and the two disk-capacity/preflight fields. The v4/v6 gate checks each listed physical option and domain field explicitly, then checks each energy field independently. The `qex` comparison is direct, so a mismatch cannot be hidden by a larger-valued field.
- DSpec trace and spectrum CSV headers match the driver-emitted contracts (`time_s,vertical_m,window_weight` and `bin,frequency_hz,real,imag`). DSpec native/profile kernel bytes and numeric tables are required to match exactly. V4/v6 kernel relative errors are scaled independently for each of A, C, F, L, N and kappa; trace and spectrum errors are scaled by their respective columns. This closes the earlier global-scale masking gaps.
- The L=3 completeness gates require seven theta rows, all 179 radial nodes, matching full and actual target point counts, and binary sizes consistent with the declared channel layout. Kernel and CSV values are checked for finiteness. DSpec’s q-dot-P check is computed against `2E` at the declared `1e-10` relative threshold.
- The checker uses the actual YSpec result keys and its driver’s native-endian, angle-major `[A,C,F,L,N]` layout. YSpec kernel mode emits no trace or spectrum table. Its shared baseline is read only to reject non-finite input values; it is not compared as a YSpec output or described as a computed YSpec trace. YSpec native/profile kernel bytes and stable result metadata are required to match exactly. The README documents this boundary.
- Profile records are checked for solver/objective identity, one root stage, finite nonnegative accounting values, and closure of the stages’ exclusive-time sum against `physical_case_total` inclusive time. The frozen drivers use the expected DSpec and YSpec profile roots.
- Cross-code kernel summaries remain explicitly descriptive and do not create a global accuracy gate or scientific accuracy claim.

One reporting detail to keep in mind: each job’s `trace_rows` summary field is sourced from `job["trace"]`; for YSpec that array is the shared baseline input. The README states this baseline is finite-checked only, so the field does not alter qualification or imply YSpec produced a trace, but readers should interpret it as baseline row count for YSpec jobs.

No remaining checker blocker was found in this static review. This PASS does not validate generated scientific artifacts or establish scientific accuracy.
